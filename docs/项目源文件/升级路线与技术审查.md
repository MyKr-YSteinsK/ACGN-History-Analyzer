## 项目价值与取舍

现有系统已经有作品身份、正式记录与收藏转换、导入预览与歧义、档期统计、系列整理和基于历史数据的复盘。用一个真实工作流把这些能力串起来，可以讲清楚什么数据可以自动匹配、哪里需要人工确认、失败后发生了什么、如何从导出恢复。现有往返导出仍依赖本地 ID，项目在旧数据库兼容、真实模型和浏览器交互上的追加证据见 STATUS.md。

| 相关项目 | 可展示能力与投入选择 |
| --- | --- |

## 推荐的第一条升级切片

在现有 Spring Boot、MySQL 和 React 上做一个可审计的记录迁移闭环。保留正式记录与收藏业务约束、旧 JSON／CSV 入口及现行档期和个人评分。使用一份合成导入文件，包含精确来源标识、同名多季歧义、未匹配行、重复行、可选空评分／备注，以及已有收藏的作品。

1. **定义迁移行为。** 明确缺失、冲突、重复和覆盖的语义。缩小首版到正式记录及其必要作品映射。集合级快照、全库备份、封面和所有第三方源单列。
2. **预览与确认。** 解析输入并保留行号，给出匹配证据、候选、将写字段和跳过原因。提交使用明确选择后的作品标识，检测预览时的关键前提是否改变。输入版本、所选标识和本次执行记录能够关联。
3. **执行与重试。** 逐行记录结果，明确哪些错误可跳过、哪些错误使整批失效。重复同一输入不能产生额外记录。重试对最终数据和收藏状态的影响可核对。现有同步与后台接口可以先共享同一写入规则。
4. **导出与恢复。** 给新导出增加版本和可移植作品映射的候选设计，保留既有 Bangumi 往返格式。将导出恢复进入不同主键序列的独立空库，对账作品标识、记录、评分、档期、备注和缺失值。冲突留给用户确认。
5. **演示与基线。** 用一份公开合成夹具录制短演示，展示歧义决策、失败后恢复以及往返对账。在同一夹具记录实际成功／跳过数、重复写入数量与失败回滚，对性能有要求时再记录批次大小、SQL 查询数和耗时分位数。

该切片的建议验收是三个可重现的结果：预览不会改变原库；同一批数据重复提交后净新增记录数为零；在不同主键的空库恢复后，按稳定身份比较的记录语义一致。预期缺失或冲突应在报告中逐行说明。既有库先在备份副本验证，失败回滚和恢复路径单测。可在验收后决定是否进一步生成与每条结论关联的年度报告。

## 后续阶段与选择

| 选择 | 用户确认的重点 | 第一个可交付结果 |
| --- | --- | --- |
| A. 保留为毕设和补充作品 | 当前用途保持个人本地维护 | 以现有代码、截图历史和事务缺陷案例做面试叙述，可按需修复真实障碍。 |
| B. 做迁移闭环，建议优先 | 授权小范围产品升级，确定输入源、数据用量和需要兼容的旧版本 | 合成数据从预览、导入、重试到跨库恢复，附对账与短演示。完成后再决定是否扩展。 |
| C. 做更大产品升级 | 已出现持续使用理由，并有独立时间预算、旧库与发布决策 | 先在模块化单体内实现稳定的数据与作业边界。若目标明确要求轻量离线或交付成本下降，再对单文件数据库、可执行打包或新前端做验证原型。 |

走 B 或 C 时，先建立独立测试库、最小回归和当前测量，再做数据边界及后端模块化。任务恢复体系、前端交互大改、真实模型供应商、与 Bangumi Side B 的数据协作，以及受控部署各自有验收，投入顺序按用户目标和证据调整。当前候选无需预先承诺账号体系、新微服务或数据库品牌切换。

停止条件建议设为：一个限定的迭代后，若无法用合成数据讲清导入、重试和恢复，也没有实际使用反馈支持继续投入，回到 A，把时间留给 RunProof 和 config-center。后续批准事项、测量结果和用户接受情况写回项目定义和状态。
